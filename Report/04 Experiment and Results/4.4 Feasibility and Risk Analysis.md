# 4.4 Feasibility and Risk Analysis

↑ [[04 Experiment and Results]]

## 4.4.1 Executive Summary

At prototype level, the system is technically feasible because it depends on available components such as a camera, a processing unit, a heart-rate sensor, and an audible alert module. The main challenges are detection accuracy, real-time processing, lighting variation, sensor noise, and integration between hardware and software modules. The project can be implemented based on the following steps: test each module separately, define detection thresholds, map detected states to alert patterns, then integrate the full system gradually. The risks are manageable if the system uses multi-sensor validation, careful threshold tuning, and controlled prototype testing before final demonstration.

## 4.4.2 Objective and Scope

This section identifies whether the proposed DMS can be implemented as a practical prototype and identifies the main technical and operational risks that may affect the system during development and testing.

- Evaluate the technical feasibility of the proposed DMS concept.
- State the assumptions required for successful prototype operation.
- Identify major risks related to sensing, processing, alerts, and integration.
- Suggest mitigation actions to reduce risk before and during Project 2.
- Clarify the dependencies that must be completed before moving to the next phase.

## 4.4.3 Technical Feasibility

The proposed system is feasible as a prototype because it uses components and methods that are commonly available in embedded systems, computer vision, and basic sensor integration. The main technical requirement is not the availability of the components, but the ability to integrate them in a reliable real-time workflow.

- **Sensing feasibility:** Camera-based monitoring can support eye-closure detection, gaze tracking, and phone-use detection. A physiological sensor can provide an additional input to strengthen the decision logic.
- **Processing feasibility:** A suitable processing unit can run lightweight image processing or machine-learning models. For prototype testing, the team can reduce camera resolution or frame rate if performance is slow.
- **Alert feasibility:** Buzzer and vibration-based alerts are simple to implement and easy to connect to the risk classification output. Different buzzer and vibration patterns can represent different severity levels.
- **Prototype feasibility:** The project prototype is feasible if it is tested under controlled conditions and gradually improved.

## 4.4.4 Key Assumptions

The feasibility assessment depends on the following assumptions. If these assumptions are not satisfied, the system may require additional hardware, better algorithms, or revised testing conditions.

- The camera has a clear and stable view of the driver's face.
- Lighting conditions are good enough for eye and face detection.
- The processing unit can analyse input data and trigger alerts with acceptable delay.
- The physiological sensor gives stable readings and is positioned correctly.
- The buzzer is loud enough to be noticed inside the vehicle and vibrations can be felt.
- The driver remains within a reasonable seating position during testing.
- The system is developed as a prototype first, not as a certified commercial automotive product.
- The team has enough time to test each subsystem before full integration.

## Table 4-2: Risk Analysis of the Proposed System

| Risk | Description | Impact | Mitigation |
| --- | --- | --- | --- |
| Face obstruction | Sunglasses, masks, or head turning may block facial features. | High | Use multiple indicators and avoid depending on one facial feature only. |
| False alarms | The system may warn the driver even when not fatigued or distracted. | Medium | Use repeated abnormal readings before strong alerts and tune thresholds carefully. |
| Missed detection | The system may fail to detect fatigue or distraction in some cases. | High | Improve test coverage, combine behavioural and physiological data, and validate thresholds. |
| Sensor noise | Heart-rate readings may fluctuate due to movement or poor contact. | Medium | Apply filtering and use physiological data as supporting evidence rather than the only decision input. |
| Real-time delay | Video processing may delay detection and alert generation. | High | Use lightweight models, reduce frame resolution if needed, and optimize the code. |
| Hardware limitations | The processing unit may not be strong enough for continuous image processing. | Medium | Benchmark performance early and select hardware based on actual prototype needs. |
| Driver discomfort | Frequent buzzer and vibration alerts may annoy the driver. | Medium | Use severity-based alert patterns and avoid alerting after isolated readings. |
| Integration issues | Camera, sensor, processor, vibration, and buzzer may not work smoothly together. | Medium | Test modules separately, then integrate step by step. |
| Privacy concerns | Camera monitoring may raise concerns because it observes the driver's face. | Medium | Process data locally where possible and avoid unnecessary image or video storage. |

## 4.4.5 Mitigation Plan

The proposed mitigation plan is based on reducing uncertainty before full integration. The team should not build the complete system at once. Instead, each subsystem should be validated separately, then connected gradually.

**Step 1: Validate the behavioural sensing module:** Test the camera module using simple scenarios such as normal face view, eye closure, gaze deviation, and phone-use examples.

**Step 2: Validate the physiological sensing module:** Check whether the heart-rate-related readings are stable and whether noise appears during movement.

**Step 3: Validate the alert module:** Create clear buzzer and vibration patterns for different risk levels and confirm that they are distinguishable.

**Step 4: Define thresholds and decision logic:** Set rules for when a condition becomes unsafe. For example, a short eye blink should not trigger the same alert as long eye closure.

**Step 5: Integrate modules gradually:** Start with one detected condition and one buzzer/vibration output, then add gaze, phone usage, and physiological support.

**Step 6: Test full prototype scenarios:** Run controlled tests for normal driving, fatigue simulation, distraction, and combined risk cases.

> [!tip] This 6-step mitigation plan maps directly onto [[5.2 Phase Two Plan]]'s five implementation phases.

## 4.4.7 Feasibility Conclusion

The proposed system relies on available hardware and practical sensing techniques, and the alert module can be implemented using simple buzzer and vibration patterns. The project is not risk-free, but the identified risks are manageable if the team follows a structured testing and integration approach, making this project feasible.

The most important success factors are reliable camera detection, acceptable processing speed, stable physiological input, and clear alert logic. Therefore, the team should proceed to Project 2 with a focus on early module testing, threshold tuning, and gradual integration.
